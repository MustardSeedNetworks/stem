# Upgrading an existing install in place — STM-23, 2026-09-25

**Question.** STM-21 automates upgrades, so first prove that upgrading an
existing install by hand is trustworthy: the service comes back on the new
version with a non-empty `uiBuildHash`, persisted config and run state
survive, and a test run and a reflector start succeed afterwards. Look
specifically for niac-go#2092's class: something the old version wrote that
the new one rejects while `/__version` still reports success.

**Answer.** The `.deb` upgrade is sound. The `.rpm` upgrade is **not**: it
ends with the service stopped and disabled while the installer prints
"installed and running" ([#1445](https://github.com/MustardSeedNetworks/stem/issues/1445),
fixed in the PR that adds this file). Nothing the old version persisted was
rejected by the new one. The audit also found a measurement defect unrelated
to upgrading ([#1446](https://github.com/MustardSeedNetworks/stem/issues/1446))
and a silent certificate replacement in `foundation`
([foundation#76](https://github.com/MustardSeedNetworks/foundation/issues/76)).

## Method

Run on dev-srv-ubuntu (Ubuntu 26.04, x86_64) in Docker containers with
systemd as PID 1 (`--privileged --cgroupns=host`), so the packages' own
maintainer scripts and `stem.service` run unmodified. All containers share one
Docker bridge. A fourth container ran v0.24.154 as the reflector the tests
point at; its `packetsReflected` counter is read before and after each test,
so a passing run is only counted when the peer actually reflected frames
(see #1446 for why the run's own verdict is not enough).

For each leg: install the old release's shipped package, configure it, then
`apt-get install` / `dnf install` the v0.24.154 package over it.

"Configured" means: first-run setup completed (or, for v0.24.105, which
predates first-run setup, `STEM_AUTH_USERNAME`/`STEM_AUTH_PASSWORD` in
`/etc/stem/environment`, as CT307 has); a Pro trial started through the
daemon; one RFC 2544 throughput run; and a reflector saved with
`stem reflect -i eth0 --profile netally --port 3842 --at-boot` and left
running. Every file under `/var/lib/stem` and `/etc/stem` was copied aside
before the upgrade and compared after it.

Stem keeps no server-side run history: the History page is a browser store.
The daemon's persisted run state is `reflector.json` (the saved reflector and
its autostart flag), `credentials.json`, and the licence file. Those are what
"run history survives" can mean on the server, and they are what was checked.

The macOS tarball leg was not run: this host is Linux, and it needs the Mac.

## Findings

### 1. An RPM upgrade leaves stem stopped and disabled — #1445, fixed here

```text
>>> Running %post scriptlet: stem-0:0.24.154-1.x86_64
>>>   The Stem is installed and running
>>> Running %preun scriptlet: stem-0:0.24.153-1.x86_64
>>> Removed '/etc/systemd/system/multi-user.target.wants/stem.service'.
>>> Running %postun scriptlet: stem-0:0.24.153-1.x86_64
>>> Stem removed. Data preserved in /var/lib/stem
```

RPM runs the old package's `%preun` after the new package's `%post`, and
`preremove.sh` stopped and disabled the service unconditionally. The journal
shows the new daemon start, autostart the reflector, and receive
`Shutdown signal received` five seconds later. This is niac-go#2092's class:
the installer reports success and the product is down, and would stay down
after a reboot. niac-go fixed the identical script in niac-go#2085; seed
carries it too ([seed#2861](https://github.com/MustardSeedNetworks/seed/issues/2861)).

The `.deb` recovers only because dpkg runs the old `prerm` before the new
`postinst`, but it still printed `Removed …stem.service` and `Stem removed`
during an upgrade, and `postinstall.sh` told an already-configured install to
"set the administrator password in setup".

**Fix.** `preremove.sh` stops and disables only on final removal (`0`,
`remove`, `purge`); `postremove.sh` says "removed" only then; the first-visit
hint prints only on a fresh install (RPM `1`, or dpkg `configure` with no
previous version).

**Proof.** The v0.24.154 binary repackaged with nfpm, once with `main`'s
scripts and once with the fixed ones, upgraded in place in fresh containers:

```text
[RPM-old-scripts] fresh stem-0.24.901: active/enabled first-visit-hint=1
[RPM-old-scripts] upgrade -> 0.24.902: inactive/disabled removed-msg=1 unit-removed=1
[RPM-fixed]       fresh stem-0.24.911: active/enabled first-visit-hint=1
[RPM-fixed]       upgrade -> 0.24.912: active/enabled first-visit-hint=0 removed-msg=0 unit-removed=0
[RPM-fixed]       remove: inactive/not-found
[DEB-old-scripts] upgrade -> 0.24.902: active/enabled first-visit-hint=1 removed-msg=1 unit-removed=1
[DEB-fixed]       fresh stem_0.24.911: active/enabled first-visit-hint=1
[DEB-fixed]       upgrade -> 0.24.912: active/enabled first-visit-hint=0 removed-msg=0 unit-removed=0
[DEB-fixed]       remove: inactive/not-found removed-msg=1 data-kept=yes
```

**Limit.** During an upgrade it is the _old_ package's `%preun` that runs. An
RPM upgrade from any release up to and including the last one shipped before
this fix still ends stopped and disabled, once, and needs
`sudo systemctl enable --now stem` afterwards. niac-go made the same trade.

### 2. A throughput run against a host that reflects nothing reports success — #1446, open

Found while checking that post-upgrade test runs were real. With the peer's
reflector filtering for NetAlly signatures (1.6 M frames received,
**0 reflected**), and again against the Docker host, which runs no reflector
and on which `tcpdump -Q in udp` saw **0** inbound frames, the run reported:

```text
{"success":true,"s":"passed","d":{"GeneratorLimited":true,"Iterations":1,
 "MaxRateMbps":730.93,"MaxRatePPS":178449.0,"OfferedRatePct":50}}
```

`rfc2544_throughput_test` stops the search on a generator-limited trial
(#1233's fix) and records it as the result without looking at its loss; the
first trial on any host that cannot reach 50 % of a 10 G line rate takes that
branch. `rfc2889_forwarding_rate_test` has the same branch. Not an upgrade
defect, but STM-23 does not close while it is open.

### 3. The upgrade silently replaces the self-signed certificate — foundation#76, open

v0.24.154 is the first release on `foundation/pkg/httpserver`, whose
`EnsureCertificate` regenerates a certificate that does not cover the
loopback IP SANs. Every pre-0.24.154 certificate lacks them, so every upgrade
replaced it (RSA-4096 `A3:A3:67:92…` → ECDSA P-256 `D4:64:4D:9B…`). Replacing
it is correct; doing it with no log line is not: an operator who ran
`stem install-ca` gets a browser warning and nothing says why. v0.24.153
logged `Generated self-signed TLS certificate`; v0.24.154 logs nothing on
generation or replacement. The fix belongs in `foundation`, then a bump here.

## What was not a defect

- v0.24.105 on a fresh install with no credentials never listens
  (`activating`, 20 restarts): that is the pre-first-run-setup crash loop
  D-STEM-3 fixed, not an upgrade problem, and why the 0.24.105 leg uses
  environment credentials.
- v0.24.105's `stem license --trial`, run as root, wrote
  `/root/.config/stem/.license`, which the daemon never reads; D-STEM-18 moved
  licence commands onto the daemon. The trial for that leg was started through
  the daemon's API.
- A post-upgrade test aimed at the NetAlly-profile reflector on the upgraded
  host was not reflected: stem's own test frames do not carry an ITO
  signature, and the filter is doing its job.
