# Upgrading an existing install in place — STM-23, 2026-09-25

**Question.** STM-21 automates upgrades, so first prove that upgrading an
existing install by hand is trustworthy: the service comes back on the new
version with a non-empty `uiBuildHash`, persisted config and run state
survive, and a test run and a reflector start succeed afterwards. Look
specifically for niac-go#2092's class: something the old version wrote that
the new one rejects while `/__version` still reports success.

**Answer.** The `.deb` upgrade is sound. The `.rpm` upgrade is **not**: it
ends with the service stopped and disabled while the installer prints
"installed and running" ([#1445](https://github.com/MustardSeedNetworks/stem/issues/1445),
fixed in the PR that adds this file). Nothing the old version persisted was
rejected by the new one. The audit also found a measurement defect unrelated
to upgrading ([#1446](https://github.com/MustardSeedNetworks/stem/issues/1446))
and a silent certificate replacement in `foundation`
([foundation#76](https://github.com/MustardSeedNetworks/foundation/issues/76)).

## Method

Run on dev-srv-ubuntu (Ubuntu 26.04, x86_64) in Docker containers with
systemd as PID 1 (`--privileged --cgroupns=host`), so the packages' own
maintainer scripts and `stem.service` run unmodified. All containers share one
Docker bridge. A fourth container ran v0.24.154 as the reflector the tests
point at; its `packetsReflected` counter is read before and after each test,
so a passing run is only counted when the peer actually reflected frames
(see #1446 for why the run's own verdict is not enough).

For each leg: install the old release's shipped package, configure it, then
`apt-get install` / `dnf install` the v0.24.154 package over it.

"Configured" means: first-run setup completed (or, for v0.24.105, which
predates first-run setup, `STEM_AUTH_USERNAME`/`STEM_AUTH_PASSWORD` in
`/etc/stem/environment`, as CT307 has); a Pro trial started through the
daemon; one RFC 2544 throughput run; and a reflector saved with
`stem reflect -i eth0 --profile netally --port 3842 --at-boot` and left
running. Every file under `/var/lib/stem` and `/etc/stem` was copied aside
before the upgrade and compared after it.

Stem keeps no server-side run history: the History page is a browser store.
The daemon's persisted run state is `reflector.json` (the saved reflector and
its autostart flag), `credentials.json`, and the licence file. Those are what
"run history survives" can mean on the server, and they are what was checked.

The macOS tarball leg ran later, on the Mac; see
[macOS tarball leg — 2026-10-10](#macos-tarball-leg--2026-10-10).

## Findings

### 1. An RPM upgrade leaves stem stopped and disabled — #1445, fixed here

```text
>>> Running %post scriptlet: stem-0:0.24.154-1.x86_64
>>>   The Stem is installed and running
>>> Running %preun scriptlet: stem-0:0.24.153-1.x86_64
>>> Removed '/etc/systemd/system/multi-user.target.wants/stem.service'.
>>> Running %postun scriptlet: stem-0:0.24.153-1.x86_64
>>> Stem removed. Data preserved in /var/lib/stem
```

RPM runs the old package's `%preun` after the new package's `%post`, and
`preremove.sh` stopped and disabled the service unconditionally. The journal
shows the new daemon start, autostart the reflector, and receive
`Shutdown signal received` five seconds later. This is niac-go#2092's class:
the installer reports success and the product is down, and would stay down
after a reboot. niac-go fixed the identical script in niac-go#2085; seed
carries it too ([seed#2861](https://github.com/MustardSeedNetworks/seed/issues/2861)).

The `.deb` recovers only because dpkg runs the old `prerm` before the new
`postinst`, but it still printed `Removed …stem.service` and `Stem removed`
during an upgrade, and `postinstall.sh` told an already-configured install to
"set the administrator password in setup".

**Fix.** `preremove.sh` stops and disables only on final removal (`0`,
`remove`, `purge`); `postremove.sh` says "removed" only then; the first-visit
hint prints only on a fresh install (RPM `1`, or dpkg `configure` with no
previous version).

**Proof.** The v0.24.154 binary repackaged with nfpm, once with `main`'s
scripts and once with the fixed ones, upgraded in place in fresh containers:

```text
[RPM-old-scripts] fresh stem-0.24.901: active/enabled first-visit-hint=1
[RPM-old-scripts] upgrade -> 0.24.902: inactive/disabled removed-msg=1 unit-removed=1
[RPM-fixed]       fresh stem-0.24.911: active/enabled first-visit-hint=1
[RPM-fixed]       upgrade -> 0.24.912: active/enabled first-visit-hint=0 removed-msg=0 unit-removed=0
[RPM-fixed]       remove: inactive/not-found
[DEB-old-scripts] upgrade -> 0.24.902: active/enabled first-visit-hint=1 removed-msg=1 unit-removed=1
[DEB-fixed]       fresh stem_0.24.911: active/enabled first-visit-hint=1
[DEB-fixed]       upgrade -> 0.24.912: active/enabled first-visit-hint=0 removed-msg=0 unit-removed=0
[DEB-fixed]       remove: inactive/not-found removed-msg=1 data-kept=yes
```

**Limit.** During an upgrade it is the _old_ package's `%preun` that runs. An
RPM upgrade from any release up to and including the last one shipped before
this fix still ends stopped and disabled, once, and needs
`sudo systemctl enable --now stem` afterwards. niac-go made the same trade.

### 2. A throughput run against a host that reflects nothing reports success — #1446, open

Found while checking that post-upgrade test runs were real. With the peer's
reflector filtering for NetAlly signatures (1.6 M frames received,
**0 reflected**), and again against the Docker host, which runs no reflector
and on which `tcpdump -Q in udp` saw **0** inbound frames, the run reported:

```text
{"success":true,"s":"passed","d":{"GeneratorLimited":true,"Iterations":1,
 "MaxRateMbps":730.93,"MaxRatePPS":178449.0,"OfferedRatePct":50}}
```

`rfc2544_throughput_test` stops the search on a generator-limited trial
(#1233's fix) and records it as the result without looking at its loss; the
first trial on any host that cannot reach 50 % of a 10 G line rate takes that
branch. `rfc2889_forwarding_rate_test` has the same branch. Not an upgrade
defect, but STM-23 does not close while it is open.

### 3. The upgrade silently replaces the self-signed certificate — foundation#76, fixed

v0.24.154 is the first release on `foundation/pkg/httpserver`, whose
`EnsureCertificate` regenerates a certificate that does not cover the
loopback IP SANs. Every pre-0.24.154 certificate lacks them, so every upgrade
replaced it (RSA-4096 `A3:A3:67:92…` → ECDSA P-256 `D4:64:4D:9B…`). Replacing
it is correct; doing it with no log line is not: an operator who ran
`stem install-ca` gets a browser warning and nothing says why. v0.24.153
logged `Generated self-signed TLS certificate`; v0.24.154 logs nothing on
generation or replacement. The fix belongs in `foundation`, then a bump here.

Fixed in foundation v0.6.0 (foundation#77) and adopted here: every pair
`EnsureCertificate` writes is logged with its reason, expiry and SHA-256
fingerprint, a replacement at WARN. Proved against the daemon on
dev-srv-ubuntu with a pre-0.24.154-shaped certificate (RSA-2048, SANs
`localhost` and `stem.local` only) in `STEM_TLS_CERTS_DIR`:

```text
$ openssl x509 -in certs/server.crt -noout -fingerprint -sha256   # before
sha256 Fingerprint=0D:0A:2D:E0:…:AF:B1:95
$ stem web -p 18544
level=WARN msg="replaced self-signed TLS certificate; re-install it wherever
  the previous one was trusted" component=stem cert_file=…/certs/server.crt
  reason="does not cover 127.0.0.1" valid_until=2027-09-25T09:11:56Z
  sha256=52:B6:04:A3:…:2E:FB:1F:53
$ openssl x509 -in certs/server.crt -noout -fingerprint -sha256   # after
sha256 Fingerprint=52:B6:04:A3:…:2E:FB:1F:53
```

A second start reused the new pair and logged no certificate line.

## What was not a defect

- v0.24.105 on a fresh install with no credentials never listens
  (`activating`, 20 restarts): that is the pre-first-run-setup crash loop
  D-STEM-3 fixed, not an upgrade problem, and why the 0.24.105 leg uses
  environment credentials.
- v0.24.105's `stem license --trial`, run as root, wrote
  `/root/.config/stem/.license`, which the daemon never reads; D-STEM-18 moved
  licence commands onto the daemon. The trial for that leg was started through
  the daemon's API.
- A post-upgrade test aimed at the NetAlly-profile reflector on the upgraded
  host was not reflected: stem's own test frames do not carry an ITO
  signature, and the filter is doing its job.

## macOS tarball leg — 2026-10-10

**Answer.** The upgrade from v0.26.6 to v0.26.14 kept every persisted file
byte-identical and kept the old password. But the licence is unreadable on
roughly every other daemon start, upgrade or not
([#1648](https://github.com/MustardSeedNetworks/stem/issues/1648), from
[foundation#108](https://github.com/MustardSeedNetworks/foundation/issues/108)).
That is niac-go#2092's class: `/__version` reports success while the install
is quietly back on Free. Two macOS-only defects were found alongside it
([#1649](https://github.com/MustardSeedNetworks/stem/issues/1649),
[#1650](https://github.com/MustardSeedNetworks/stem/issues/1650)).

### Method

Run on the owner's Mac (macOS 27.2, arm64) over `ssh mac`. The tarballs
`stem-0.26.6-darwin-arm64.tar.gz` and `stem-0.26.14-darwin-arm64.tar.gz`
came from the GitHub releases and passed `shasum -a 256 -c` against each
release's `checksums.txt`.

There is no passwordless sudo on that machine, so the documented system
install (`/usr/local/stem`, a LaunchDaemon run as root) was not possible. The
leg ran the shipped `launchd/com.stem.plist` instead as a LaunchAgent in the
user's `gui/501` domain. The plist was unchanged except for one substitution:
`/usr/local/stem` became a scratch prefix. So the daemon ran under launchd with
the shipped `ProgramArguments`, `WorkingDirectory`, `HOME`, `KeepAlive` and
log paths, but as the user rather than as root.

The leg had three steps:

1. **Install and configure v0.26.6.** Install, `launchctl bootstrap`,
   first-run setup through `/api/v1/setup/complete`, a login,
   `stem license --trial`, and `stem reflect -i en0 --profile netally --port
   3842 --at-boot`.
2. **Upgrade in place.** `launchctl bootout`, extract the v0.26.14 tarball
   over the prefix, rewrite the plist the same way, `launchctl bootstrap`.
3. **Clean up.** Everything (agent, prefix, plist) was removed afterwards, and
   nothing was left listening.

### Results

| Check | Result |
| --- | --- |
| Upgrade | `launchctl print`: `state = running`, `runs = 1`, never exited |
| `/__version` | 0.26.6 (`uiBuildHash 536d18c1…`) → 0.26.14 (`uiBuildHash be37b9c4…`) |
| Persisted files | `credentials.json`, `reflector.json`, `.config/stem/.license`, `certs/server.{crt,key}` byte-identical; only `.daemon.json` and `.instance.lock` changed (expected) |
| Setup and login | `needsSetup:false`; old password logs in (200), a wrong one is refused (401) |
| TLS certificate | Kept: the same fingerprint `B6:74:2C:94…` before and after |
| Licence | **Lost on the first post-upgrade start**: "Not Activated", `event=license.unusable status=malformed` (#1648) |
| Reflector start | Not possible on macOS: the darwin build is `CGO_ENABLED=0` and has no dataplane. Autostart fails every boot (#1650) |
| Test run | Not possible on macOS for the same reason. Capabilities still claim test-master support (#1650) |

The acceptance clause "a test run and a reflector start succeed after the
upgrade" cannot hold on macOS. The published darwin build carries no
dataplane, and `docs/DEPLOYMENT.md` lists macOS as development/testing only.
What the leg can establish is that the daemon, its configuration and its
entitlements survive. The first two do; the entitlements do not.

### 4. A macOS daemon's licence decrypts on some starts only — #1648, foundation#108

The licence file is encrypted under the device fingerprint.
`foundation/pkg/license` builds that fingerprint partly from the disk serial,
read with `system_profiler` under a 5 s timeout, and substitutes the constant
`DARWIN-DISK` when the timeout expires. From a shell, `system_profiler`
answers in 0.1–0.3 s. As a launchd job, foundation's own
`GenerateFingerprint` took 9–11 s:

```text
ssh shell (6 runs):   hash=8485C367E0AD2E6F disk=0ba01e0162e56225 took=213-375ms
launchd job (3 runs): hash=A56C05CFD5761D54 disk=DARWIN-DISK      took=9.035s / 9.583s / 11.434s
```

The trial was started while v0.26.6 had fingerprint `A56C05CF…`. Restarting
one binary, with nothing else changed:

```text
0.26.14 start (the upgrade)   Device ID 8485C367E0AD2E6F  Not Activated
0.26.14 restart 1             Device ID A56C05CFD5761D54
0.26.14 restart 2             Device ID 8485C367E0AD2E6F
0.26.6 binary, same data      Device ID A56C05CFD5761D54  Trial Mode
0.26.14 again                 Device ID 8485C367E0AD2E6F  Not Activated
```

The upgrade did not damage anything. It is one restart, and any restart can
flip the fingerprint. Seed uses the same package on macOS.

### 5. The CLI looks for a macOS daemon in the wrong directory — #1649

`daemonconn.SearchDirs` tries `STEM_DATA_DIR`, then `/var/lib/stem`, then the
working directory. The launchd install keeps its state in `/usr/local/stem`.
The leg drove its daemon only by exporting `STEM_DATA_DIR` by hand.

### 6. macOS advertises what it cannot do — #1650

`/api/v1/capabilities` reports `testMaster.supported: true` on darwin, but
every test fails with `dataplane unavailable`. A reflector start returns a
`500 INTERNAL_ERROR` for a known platform limit, and still saves
`autostart: true`, so every later start logs `reflector.autostart.failed`.

## macOS re-check — 2026-10-11

**Answer.** #1649 and #1650 are fixed in v0.26.16. The re-check found one
new defect in how the CLI words the refusal #1650's fix introduced
([#1657](https://github.com/MustardSeedNetworks/stem/issues/1657), fixed in
the change that adds this section) and one copy defect in the no-daemon hint
([#1658](https://github.com/MustardSeedNetworks/stem/issues/1658), open).

Same method as the 2026-10-10 leg: the v0.26.14 and v0.26.16 darwin-arm64
tarballs (both pass `shasum -a 256 -c` against their `checksums.txt`), the
shipped plist as a `gui/501` LaunchAgent under a scratch prefix, first-run
setup, `stem license --trial`, and `stem reflect -i en0 --profile netally
--port 3842 --at-boot`, then an in-place upgrade to v0.26.16. Everything was
removed afterwards; nothing was left listening.

### 7. The CLI calls a platform refusal a rejected credential — #1657, fixed

```text
$ stem reflect -i en0 --profile netally --port 3842
Error: the daemon rejected this credential (403): CGO + Linux required
```

`daemonclient` read every 403 as a credential problem. A 403 is a refusal of
the request: a scope denial, a CSRF failure, or, since #1654, a platform with
no dataplane. It now reads `the daemon refused this request (403): …`; 401
remains the credential case.

### 8. The no-daemon hint names systemctl on macOS — #1658, fixed

With no daemon found, the CLI said "Start it with 'systemctl start stem'" on
every OS. `docs/DEPLOYMENT.md` now documents the launchd commands, and the
hint names `sudo launchctl kickstart system/com.stem` on macOS and only
`stem web` on Windows, which ships no service.

### Stale autostart from an earlier release

A `reflector.json` that v0.26.14 saved with `autostart: true` survives the
upgrade, and v0.26.16 logs `reflector.autostart.failed` on every start. The
v0.26.16 daemon refuses the reflector request that would rewrite it, so on
macOS the file has to be deleted by hand. This is state written by the
defect that #1650 fixed; pre-1.0, it gets no migration.
