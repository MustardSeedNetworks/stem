# Y.1564 runs through the daemon — #1411 on the wire, 2026-09-25

**Question.** ST-2's last acceptance clause runs a two-step plan, RFC 2544
throughput then Y.1564, against a licensed real daemon. Its named blockers
(#1231, #1239) are closed, so the bench was rebuilt to take it. The Y.1564 step
failed in under a millisecond:

```text
[Y.1564] Service Configuration Test: service=1 (Service-1), CIR=50.00 Mbps
[Y.1564]   Step 1: 0% CIR (0.00 Mbps)
[Y.1564] Step 1 failed: -22
```

That is [#1411](https://github.com/MustardSeedNetworks/stem/issues/1411): every
Y.1564 run the daemon starts fails before sending a frame. A second step that
fails instantly can never be observed "running", so the clause cannot be taken
until this is fixed.

**Answer.** Fixed. `y1564_config` and `y1564_perf` started through
`POST /api/v1/test/start` run every step at 25/50/75/100 % of the configured
CIR, and a capture on the reflector counts the frames.

| Claim | Result | Evidence |
| --- | --- | --- |
| On `origin/main` the daemon's executor cannot run Y.1564 | **REPRODUCED** | `TestY1564ConfigReflectedEveryStep` / `TestY1564PerfReflected` built from `d946ba1`: both `failed: -22` |
| With the fix the same executor runs every step | **PASS** | same tests: steps at 25/50/75/100 %, tx 588 / 1173 / 1760 / 2331, the reflector returned each |
| The default config carries the step table | **PASS** | `test_y1564_daemon_path`: fails on main with `step 1: 0.0%, want 25.0%` |
| Y.1564 prepares its own platform | **PASS** | same test: fails on main with `-22` once the table is fixed, passes with the fix |
| The frames are on the wire, at the stepped rate | **PROVEN** | reflector capture: ~587 / 1175 / 1763 / 2350 pps per second of the run, 0 dropped by kernel |

## The two holes

Both are in the Go-to-C hand-off, as the issue diagnosed:

1. **No step table.** `rfc2544_default_config` never called
   `y1564_default_config`, and the daemon builds every context from it, so
   `config_steps` was all zeros. It now does. `step_duration_sec` had the same
   gap one layer up: the operator's `configStepDuration` reached `Params` and
   stopped there. It now crosses `Context.Configure` as
   `Config.Y1564StepDuration`; zero keeps the dataplane's 60 s default.
2. **No platform.** Only the RFC 2544 entry points prepared one, and
   `y1564_run_step` returned `-EINVAL` on a NULL platform without a log line.
   `prepare_platform` is now `rfc2544_prepare_platform`, declared in
   `rfc2544_internal.h`, and `y1564_run_step` calls it first — the same
   preferred-then-fallback selection every other test uses.

## Bench

dev-srv-ubuntu (Ubuntu 26.04, x86_64). Two unprivileged Docker containers
(`ubuntu:26.04` plus `libxdp1 libbpf1 tcpdump`, `--cap-add NET_RAW
--cap-add NET_ADMIN`, so AF_XDP fails and the AF_PACKET fallback runs) on one
bridge: reflector `172.18.0.2` running `stem reflect -i eth0`, test master
`172.18.0.3`. Both run the host's `CGO_ENABLED=1` `make build` of this branch
through `scripts/e2e-daemon.sh`. The test master's trial came from
`stem license --trial` (a fresh container is a fresh device fingerprint).
Throwaway credentials; both containers are removed afterwards.

10 Mbps at 512 bytes is 2,349.6 frames a second, so the four plateaus are the

captured.

## Found, not fixed here

- **rx exceeds tx in every step** —
  [#1457](https://github.com/MustardSeedNetworks/stem/issues/1457). A frame
  sent during warmup and reflected after the counters reset is counted as
  received, so FLR clamps to 0 and a few in-flight frames can hide loss above
  the 0.01 % threshold.
- **`--trials 1` still echoes `trials: 3`** in the CLI's step config, as
  `STM-13_WIRE_2026-09-14.md` recorded. Still observed, not diagnosed.

## What this does not close

ST-2 clause 3 itself: the Playwright spec that selects RFC 2544 throughput and
Y.1564 in the UI and asserts both steps on `/api/v1/stats` (the plan's
`/api/v1/test/status` does not exist; the run plan is published on
`/api/v1/stats`). This bench is its host.
