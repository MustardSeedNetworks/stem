# Does the #1217 fix move frames? — the wire proof, 2026-09-14

**Question.** `STM-13_CONTAINERS_2026-09-14.md` closed with four of five
prerequisites met and the fifth — "an RFC 2544 run moves real frames between
them" — failing as [#1217](https://github.com/MustardSeedNetworks/stem/issues/1217):
a run asked for five seconds finished in about a millisecond, transmitted
nothing, and returned `"success": true` with `Iterations: 0`. PR
[#1221](https://github.com/MustardSeedNetworks/stem/pull/1221) fixed that in Go
and said `Related to #1217`, not `Fixes`, because nothing had been proven on a
wire. This is that proof.

**Answer.** Both halves of #1217 are fixed and are now proven on a real wire:
the binary search runs, frames cross both interfaces, and the reflector
reflects them. Proving it needed one scratch change that is **not** part of the
fix, and that change is itself a product defect — the test master cannot select
AF_PACKET. Three new defects were found, one of them larger than #1217.

| Claim | Result | Evidence |
| --- | --- | --- |
| #1217 half (a): the search runs and frames move | **PROVEN** | `Iterations: 10` (was `0`); ~72 s for ten trials of `-d 5` (was ~1 ms); 8,095 signature frames captured on the reflector, 16,207 on the sender (tx plus reflected). |
| End-to-end reflection of test-master traffic | **PROVEN** (first time) | Sender-side capture holds `192.168.64.52.3842 > 192.168.64.53.12345` — the reflector returning the test master's own frames. |
| #1217 half (b): the `Iterations == 0` guard fires | **PROVEN** | A pre-fix build returns `throughput test ran no iterations: no frames were transmitted` where it used to return `"success": true`. |
| The reported throughput is a measurement | **NO — [#1233](https://github.com/MustardSeedNetworks/stem/issues/1233)** | 9990.23 Mbps / 14,866,419 pps / 99.90 % reported over a link that carried ~110 pps. |
| A reflector can be restarted in one daemon lifetime | **NO — [#1231](https://github.com/MustardSeedNetworks/stem/issues/1231)** | The first run drops the daemon to uid 65534; every later raw socket is `EPERM`. |
| The test master runs where AF_XDP does not | **NO — [#1232](https://github.com/MustardSeedNetworks/stem/issues/1232)** | `Failed to create UMEM` → `Trial failed: -5`, with no runtime fallback and `force_packet` unreachable from Go. |

## Bench

Two Apple containers on one L2 segment, `debian:trixie-slim`, on the
2026-09-14 recipe from the previous record: the binary is a `CGO_ENABLED=1`
linux/arm64 build of `77645a4` made in `golang:1.27.0-trixie` (gcc-14; gcc-12
cannot compile this tree), with the UI built on the host first so `//go:embed`
has something to read. Runtime packages in each container: `libxdp1 libbpf1
tcpdump iproute2 curl procps`.

```json
{"version":"v0.24.113-1-g77645a4","commit":"77645a4",
 "buildTime":"2026-09-15T02:35:25Z",
 "uiBuildHash":"3a3100d2f1502cf1a0d2bedc42e3f853"}
```

`192.168.64.52` runs the reflector, `192.168.64.53` the test master with a
fresh 14-day trial activated **before** `stem web` starts. Both daemons need
`STEM_AUTH_USERNAME` / `STEM_AUTH_PASSWORD`. Throwaway credentials were used
and both containers were destroyed afterwards.

Two things the previous record did not know:

- **`--peer` is required and is undocumented.** Without it `POST
  /api/v1/test/start` answers `400` ("A peer is required for test traffic",
  `internal/api/handlers_testing.go:60`) and the CLI prints only `Error: daemon
  returned 400`. `stem --help` lists neither `--peer` nor `--peer-port` under
  TEST OPTIONS, though `cmd/stem/cmd_testmaster.go:83` defines both.
- **`--trials 1` does not reach the run.** The config echoed back in the result
  says `"trials": 3` for every run below. Not filed separately; it is the same
  boundary #1217 and #1232 are about, and the throughput search ignores it.

## The scratch change, and why it was needed

The first unmodified run failed before it transmitted anything:

```text
[534.363] [INFO] Throughput test: frame_size=64
[534.364] [INFO] Platform: AF_XDP (high performance)
[xdp] Warning: Failed to increase RLIMIT_MEMLOCK
[xdp] Failed to create UMEM: Address family not supported by protocol
[534.364] [ERROR] Failed to initialize platform
[534.364] [ERROR] Trial failed: -5
```

`select_platform` picks AF_XDP whenever the build saw `<linux/if_xdp.h>` and
never falls back; the reflector, on the same host, falls back to AF_PACKET and
works. The only way to reach AF_PACKET is `config.force_packet`, which nothing
outside two C tests sets. That is **[#1232](https://github.com/MustardSeedNetworks/stem/issues/1232)**.

So the test-master binary for the runs below carries one scratch line —
`src/dataplane/common/core.c:195`, `if (ctx->config.force_packet)` replaced by
`if (true)` — and **nothing else**. It is not in this PR and must not be
merged. The reflector ran the unmodified binary throughout. The scratch line
changes which platform is selected; it does not touch the Go-to-C config
boundary that #1221 repaired, which is what is being proven.

## Half (a) — the search runs, and the frames are real

```text

    --peer 192.168.64.52 --json
Run stem-46b08bd4ed09e462-2 started
...
      "result": {
        "status": "completed", "testType": "rfc2544_throughput",
        "module": "benchmark", "success": true,
        "data": { "FrameSize": 64, "Iterations": 10,

                  "MaxRatePct": 99.90234375 }

```

Captures taken on both interfaces for the whole run, `0 packets dropped by
kernel` on both:

```text
reflector 192.168.64.52 : 8112 captured, 8095 of them the 18-byte signature
sender    192.168.64.53 : 16207 captured
02:45:43.276359 IP 192.168.64.53.12345 > 192.168.64.52.3842: UDP, length 18
02:45:43.328826 IP 192.168.64.52.3842 > 192.168.64.53.12345: UDP, length 18
```

The second line is the reflector returning the test master's frames — the
first time reflection of RFC 2544 traffic has been observed anywhere. The
previous record could claim only that the dataplane _loads_.

## Half (b) — the guard fires where it used to report success

The row's wording ("a _pre-fix_ binary must fail with `throughput test ran no
iterations`") cannot be taken literally: a binary from before #1221 has no such
guard, so it can only report the old false success. What the clause is really
asking is whether the new guard catches the old behaviour. So the binary for
this run is `77645a4` with `InitialRatePct` and `MaxIterations` in
`buildDataplaneConfig` restored to the zeros #1221 removed — the guard present,
the defect reintroduced:

```text
$ stem test -i eth0 -t rfc2544_throughput -d 5 --frame-sizes 64 --trials 1 \
    --peer 192.168.64.52 --json
real 0m0.102s
  "status": "error"
      "status": "failed"
        "error": "throughput test ran no iterations: no frames were transmitted"
```

Same command, same bench, `"success": true` before the guard and a named
failure after it.

## What the run found that the row did not predict

**[#1233](https://github.com/MustardSeedNetworks/stem/issues/1233) — the
reported rate is the offered rate, not a measurement.** The passing run above
claims 9990.23 Mbps and 14,866,419 pps at 99.90 % of line rate with zero loss.
The wire carried 8,095 frames in 72 seconds, a flat ~110 pps from first second
to last. At 64 bytes, 99.90 % of 10 Gbps is ~14.8 Mpps, so a single 5-second
trial should have offered ~74 M frames and ten of them ~743 M. The search
converges because the sender offered ~8,095 frames and got ~8,095 back, so
measured loss is 0.000 % at every step; `MaxRatePct` is then the configured
rate the search settled on and the Mbps and pps figures are derived from it.
None of the three is a measurement of what left the interface. This is the
same family as #1217 and worse: #1217 reported _nothing measured_ as success,
this reports _a fiction_ as success. `Latency.Count` is `0` in the same
"successful" result.

**[#1231](https://github.com/MustardSeedNetworks/stem/issues/1231) — the
daemon drops its own privileges.** The reflector's `drop_privileges`
(`src/reflector/util.c:375-420`) setuids to `nobody`. Under STM-20 that runs
inside the long-lived `stem web` process, and glibc propagates it to every
thread:

```text
BEFORE: Uid: 0 0 0 0     CapEff: 00000000a80425fb
[INFO] Dropped privileges to nobody (uid=65534, gid=65534)
AFTER (/proc/PID/task/*/status):  8 threads, all Uid 65534
```

Every later `socket(AF_PACKET, ...)` is then `EPERM` and the API answers a
bare `500`. It cost this session three false starts before the cause was
found; CT307 has never shown it because it starts one reflector at boot and
never restarts it.

## What this leaves

- **#1217** — both halves fixed and proven. The issue can close on this
  evidence.
- **ST-2 clause 3** — no longer blocked on #1217. It is blocked on
  [#1232](https://github.com/MustardSeedNetworks/stem/issues/1232): an
  unmodified binary cannot run RFC 2544 in these containers at all. With #1232
  fixed, the bench in this file is a viable host for the clause. Whether the
  clause should also assert a non-zero, _credible_ measurement per step is now
  sharper than when it was asked on #1078: as written it would have passed on
  the 99.90 %-of-nothing run above.
- **STM-13's RFC 2544 / Y.1564 legs** — still TODO, and now blocked on #1232
  and #1233 rather than on #1217. #1233 in particular means no per-platform
  throughput number recorded before it is fixed can be trusted, on the dev
  servers or anywhere else.
